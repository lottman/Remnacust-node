# Совместимость с нодами Remnawave

## Приватный канал конфигурации и webhook — не выпущено

Нода создаёт `api.sock` и `internal.sock` в одном случайном каталоге `/run/remnacust-xray-<id>` с правами `0700`. Внутренний HTTP-сокет получает права `0600`; проверяются имя, тип, владелец и права каталога. Это закрывает доступ обычных пользователей хоста, даже если они узнают служебный URL из аргументов процесса. JWT/mTLS внешнего API и проверка токена внутреннего HTTP сохраняются.

Генератор передаёт файловый Unix-адрес webhook без префикса `@`. При восстановлении ядро заменяет адрес и токен служебных webhook из прежнего abstract-формата и нового приватного файлового формата на адрес текущего запуска. Управляющий API тоже получает новый адрес и права 0600: исправлено имя обычного служебного inbound и добавлен перенос прямого API Lua-профиля. Пользовательские HTTP(S)-webhook и произвольные файловые адреса остаются прежними. Это изменение служебного канала не меняет клиентские конфигурации.

При запуске агент восстанавливает совместимое ядро из локального checkpoint: проверяет владельца/права/тип файла и каталога, поддержку runtime cache, наличие работающего процесса и готовность приватного API. Уже работающий процесс не перезапускается; административная пауза сохраняется. Без checkpoint новая нода ждёт первичную конфигурацию. На реальном контейнере проверены два последовательных перезапуска без панели: обычный профиль и Lua-профиль продолжили передачу данных из кеша, затем приняли live-обновление через новый API-сокет без смены PID.

## Получение подготовленного пакета при восстановлении — готовится к выпуску

Новый внутренний `POST /node/xray/usage-receipts/recovery-sample` принимает сохранённый запрос следующего пакета. Он доступен с авторизацией панели и объявляется флагом `quotaRecoverySamplesSupported`. Требуются подтверждённая пауза `FENCED`, её поколение и digest, текущий работающий процесс ядра и экземпляр приватного журнала. Проверки выполняются до и после команды под общим барьером управления нодой.

Запрос привязан к подготовке панели, исходному файлу журнала и предыдущему ACK. Номер следующего пакета должен точно следовать за подтверждённым. Если ожидающего пакета ещё нет, исходный файл обязан совпадать по SHA-256, а процесс запрошенного пакета — с работающим ядром. Если пакет уже сохранён, возвращается его содержимое без нового снятия счётчиков; у него может остаться старый процесс ядра. Номер и digest заранее сохранённого пакета нельзя подменить. Неподтверждённый исход требует повтора того же запроса.

После выполнения команда повторно читает приватный журнал и сверяет его с нативным ответом. Одного успешного вывода CLI недостаточно. Перезапуск ядра или несовпадение журнала оставляют исход неопределённым и данные сохранёнными для проверки. Команда ничего не подтверждает, не списывает и не снимает общую паузу. Форматы клиентских приложений этим внутренним API не меняются.

Проверки: полный набор ноды на Linux / Node 24.21 — 154 успешных теста без пропусков. Проверены JWT, неправильные и устаревшие привязки, отсутствие сохранённого результата, потеря ответа после записи, повтор после смены работающего ядра и взаимное исключение с управлением ядром. Панель и нода принимают одну и ту же проверенную структуру запроса и ответа. Дополнительно пройдена связка с настоящей PostgreSQL и контроллером ноды; нативный CLI в ней управляемый, а полного установленного сквозного сценария ещё нет.

## Подтверждение исходного расхода при восстановлении — готовится к выпуску

Новый внутренний `POST /node/xray/usage-receipts/recovery-ack` принимает только ACK, подписанный авторизацией панели. Поддержка объявляется флагом `quotaRecoveryReceiptsSupported`. Команда требует текущую подтверждённую паузу `FENCED`, совпадение поколения и digest паузы, работающего ядра и экземпляра приватного журнала. Она использует тот же барьер управления, что и пауза, и не разрешает обычный ACK в режиме восстановления.

Приватный журнал читается с проверкой формата, размера, контрольной суммы, точных строковых 64-битных номеров, порядка счётчиков и digest исходного пакета. Для первого ACK также проверяется SHA-256 оригинального файла. Успех подтверждается повторным чтением сохранённого журнала, а не одним ответом процесса. Повтор после потери ответа подтверждает только тот же номер и digest. Если уже появился следующий ожидающий пакет, он сохраняется и возвращается явно; более поздний ACK нельзя выдать за доказательство исходного.

Работающее ядро и ядро исходного пакета проверяются раздельно: после перезапуска старый пакет не переписывается. Нода не имеет доступа к SQL панели; проверка финансового решения и сохранение намерения доставки выполняются панелью. Команда не выдаёт новые резервы и не снимает общую паузу. Полный автоматический координатор возобновления ещё не завершён; клиентские протоколы этой внутренней командой не меняются.

Проверки этого этапа: 150 тестов ноды на Linux прошли без пропусков; проверка типов прошла. Покрыты повреждённый журнал, неправильные привязки, потеря ответа, перезапуск, следующий пакет и HTTP/JWT. Это проверки компонентов, не подтверждение полного установленного сценария панели с нодой.

## Готовящиеся изменения после импорта Xray 26.10.10

Изменения пока не выпущены. В обычном профиле с `routing.script` нода оставляет код маршрутизации неизменным и подключает служебный API напрямую к закрытому Unix-сокету `0600`. Выбранный официальный Xray v26.10.10 поддерживает Lua-файлы. Встроенные `base64:`/`base64+gzip:` из последующих коммитов не включены. Обычные профили без Lua используют прежний служебный inbound и правило, что сохраняет совместимость с прежними ядрами.

Плагин Torrent Blocker добавляет обычные rules и поэтому несовместим с Lua. Нода явно отклоняет такую комбинацию до запуска/применения; защита не отключается молча. Для этого режима нужно отключить плагин или перенести блокировку в Lua. Изменение способа API при переходе существующего профиля на Lua может требовать явного технического перезапуска: live-применение не меняет служебный listener и не делает скрытый restart.

Генератор сохраняет все заданные `policy.levels`, включая ненулевые уровни, и включает учёт трафика на каждом. `statsUserOnline` зависит от фактического `NET_ADMIN`, как и раньше. Профили не изменяются на месте при подготовке служебных полей.

Проверены 97 тестов ноды в Linux, TypeScript, сохранение исходного Lua/политик и настоящий запуск сгенерированного Lua-профиля в Xray: закрытый сокет, статистика, смена маршрута и сохранение старого TCP-потока. Полный аудит всех функций, многопрофильная изоляция и финальный выпуск ещё не завершены.

## Доставка плана портов и обновление контейнера — готовится к выпуску

Для нод с сохранённым планом портов панель назначает владельца операции и возрастающий строковый счётчик. Нода сохраняет их до изменения плагина или конфигурации и отклоняет запросы старого владельца, в том числе после переподключения и пересоздания контейнера. Запоздалый ответ не подтверждает новый план и не снимает признак подключения другой операции. Это относится к управляемым планам, включая подтверждённый переход в обычный режим; старые ноды без плана сохраняют прежний протокол.

Файл `/var/lib/remnanode/core/port-plan-state.json` версии 2 переносится вместе с постоянным состоянием ноды. Новая нода читает и версии 1, и 2. Перед заменой контейнера установщик проверяет поддержку версии 2 в загрузочном скрипте и коде приложения кандидата; прежний образ, который проигнорирует владельца операции, отклоняется. Отключение отдельных портов позволяет использовать обычное ядро после подтверждения, но не разрешает терять состояние доставки при откате агента. Не удаляйте журнал для обхода проверки.

Изменения плагина помечаются в этом же журнале. После перезапуска процесса пустой кеш плагина не позволяет пропустить его удаление или изменение. Неизменившаяся подтверждённая конфигурация сохраняет быстрый путь без повторного запуска ядра; изменившиеся конфигурация, интеграции или метаданные проходят полное применение.

## Базовая совместимость

Панель Remnacust 1.1.1 выбирает формат запросов по версии агента. Для старых нод она отправляет обычный JSON и выполняет операции с пользователями по одному, если массового API ещё нет. Нода не должна обновляться только ради подключения к панели.

| Remnawave Node | Соединение и API |
| --- | --- |
| 1.0.0–1.4.0 | Старый HTTP API, исходный конфиг Xray; удаление пользователя с тегами inbound. HTTP нужно разрешить явно для конкретного адреса и порта. |
| 1.5.0–2.2.3 | mTLS, исходный конфиг, JSON без сжатия. Массовые операции выполняются через отдельные запросы. |
| 2.3.0–2.3.2 | Zstd, конфиг с служебными параметрами и объединённая статистика. |
| 2.5.0–2.6.1 | Массовое добавление и удаление пользователей. |
| 2.7.0–3.2.2 | Плагины, сведения о системе и загрузке ресурсов. |
| 3.3.0–3.4.1 | Современный API, включая функции проверки геолокации. |
| Remnacust Node 1.1.1 | Современный API с расширениями нашего ядра; собственная нумерация версий. |

Если старый агент не сообщает CPU, RAM или свою версию, панель показывает отсутствие данных. Неизвестная версия не превращается в нулевую и сама по себе не запрещает запуск профиля.

Геопроверка доступна в Remnacust Node начиная с 1.1.1 и в стандартной Remnawave Node начиная с 3.3.0. Панель учитывает собственную нумерацию Remnacust и метку сборки в версии агента. Недоступность этой отдельной кнопки на старой ноде не запрещает обычную работу профиля и подписок.

## Подключение

Для нод с mTLS сохраните действующий ключ или сертификат и управляющий порт. Не заменяйте их новым случайным значением при переносе панели. Ошибка TLS или авторизации не вызывает переход на HTTP.

Ноды 1.0.0–1.4.0 обслуживают старый HTTP API. Подключайте такой агент через защищённый туннель или доверенную закрытую сеть. В `.env` панели перечислите только разрешённые адреса и порты:

```dotenv
REMNACUST_LEGACY_HTTP_NODES=10.20.0.2:2222,10.20.0.3:2222
```

Адрес должен быть доступен из контейнера панели и совпадать с адресом ноды в интерфейсе. Соседние порты остаются на HTTPS. `127.0.0.1` внутри контейнера указывает на этот контейнер, поэтому для туннеля на Docker-хосте нужен адрес, доступный из его сети. После изменения `.env` пересоздайте контейнер панели, чтобы применить окружение.

## Какие функции зависят от ядра

Обычные пользователи, подписки, профили и учёт трафика работают через API соответствующей версии агента. Поддержка протокола, транспорта и параметров конфигурации зависит от установленного Xray. Панель не добавляет MASQUE, Hysteria или новый транспорт в старое ядро.

Жёсткие ограничения отдельных хостов и тегов и немедленный отзыв соединений устройства требуют Remnacust Node и нашего Xray. Установка стандартного агента не даёт ему этих возможностей. Хост с настроенными ограничениями требует поддержки этих ограничений на ноде; само наличие записи в подписке не подтверждает их применение или работоспособность подключения. Обычное подтверждение удаления пользователя не считается подтверждением разрыва уже открытых соединений.

Наличие хоста в подписке определяется его видимостью, разрешениями пользователя, сквадами и действующими лимитами. Потеря связи с управляющим API ноды не исключает разрешённый хост. Панель сохраняет его индивидуальный ключ; общий ключ пользователя вместо него не подставляется. Доставка ключей и политики ноде выполняется отдельно, а новые данные входят в конфигурацию при следующем запуске ноды. Пока сервер недоступен, запись остаётся в клиенте, но подключение может не работать. Проверка отзыва доступа на всех необходимых нодах и блокировки устройств сохраняются.

Если настроена общая квота, отсутствие свежего учёта расхода может блокировать соответствующую группу. Эта проверка предотвращает обход лимита и не должна отключаться ради успешного HTTP-ответа.

## Если нода требует обновления

Фиолетовый значок с тем же символом, что у работающей ноды, означает: Xray работает, но установленный агент не поддерживает нужную этому профилю изоляцию хостов v2. В примечании указано обновление до Remnacust Node 1.1.1 с нашим Xray. Старые агенты подходят для обычных профилей; наличие квот, ограничения скорости и правил отдельных хостов требует нашего расширения.

Панель сохраняет работающую конфигурацию и не отправляет новую, пока её правила не подтверждены. Это не подтверждение применения настроенных ограничений на старом ядре. Настройки хостов, профилей, сквадов, квот и пользователей при этом не меняются. Если Xray остановлен или нода недоступна, значок остаётся значком неисправной ноды.

Временный сбой синхронизации на совместимой ноде показывается отдельным предупреждением. Панель повторяет применение ожидающей конфигурации не чаще раза в минуту. После успешного обновления агента, применения политики и запуска конфигурации предупреждение исчезает. Нельзя обойти проверку поддержки расширения, подавив ошибку или подставив общий ключ пользователя.


Исходные материалы: [официальные теги Remnawave Node](https://github.com/remnawave/node/tags), [установка ноды](https://docs.rw/docs/install/install-node).


## Подготовка резервов (готовится к выпуску)

Новые выдачи используют `remnacust-quota-registrations-v1`: приватный журнал подтверждается до активации. Подготовленный резерв не пропускает трафик. Отмена создаёт постоянную закрытую запись; использованный резерв сохраняет расход. Для неизвестного идентификатора отмена с нулём разрешена лишь при сохранённом в панели доказательстве отсутствия попытки активации. Старые выдачи не переводятся в этот режим задним числом.

После перехода версия журнала не понижается. Загрузчик, проверка выбранного ядра и установщик проверяют совместимость приложения и ядра. Удаление политики не разрешает несовместимый откат. Состояние `/var/lib/remnanode/quota/ledger.json` переносится вместе с существующими приватными данными; очищать его при обновлении нельзя. Формат клиентских конфигураций не меняется. Проверены настоящий VLESS TCP, Linux-тесты ноды и Docker-проверка обновления. Полное восстановление старых копий и сквозной аудит панели/ноды ещё не завершены.


### Контрольная позиция журнала (готовится к выпуску)

`remnacust-quota-watermarks-v1` — следующая версия приватного журнала. Политика содержит `quotaCheckpoint: { instance, sequence }`; `sequence` передаётся строкой без потери точности. Ядро отвергает журнал ниже этой позиции и политику ниже уже сохранённой границы. Холодный запуск проверяет исходную политику до открытия портов. Загрузчик и управляемый выбор ядра проверяют те же условия. Обновление сохраняет журнал, а несовместимый образ не заменяет ноду. Панель недоступна — актуальные локальные резервы продолжают работать. Это не восстанавливает потерянные сведения между копиями и не заменяет административную сверку.


## Временная политика при восстановлении (готовится к выпуску)

Нода поддерживает авторизованный `POST /node/xray/host-policy/quota-recovery-policy`. Запрос содержит только `requestId`, `generation`, `coreProcessId`, `instance`, `previous` (SHA-256 действующей блокировки) и строковую `policyRevision`. Произвольный JSON политики через этот метод не принимается.

Нода берёт свою сохранённую политику, сохраняет привязки пользователей, хостов, разрешения и коэффициенты, включает `fenceAll` у всех групп и удаляет активные выдачи и команды регистрации из новой политики. Это не удаляет журнал уже выданных резервов и их расход. Метод работает только при подтверждённой общей блокировке `FENCED`; обычное обновление политики во время неё запрещено. Подтверждение связано с тем же процессом ядра, журналом, ревизией и блокировкой. Перезапуск ядра или изменение источника не дают успешного ответа.

На стороне панели транспорт дополнительно проверяет точное соответствие подтверждения запросу. `RELEASED`, чужой запрос, другой журнал или поколение восстановления отвергаются. Недоступность ноды остаётся ошибкой, а не успешным применением.

Это подготовительный этап. Полный координатор возобновления, подтверждение сохранённого трафика и выдача новых резервов после восстановления ещё не завершены. Метод сам не снимает общую блокировку, не подтверждает получение трафика и не разрешает расходование новой квоты.

Проверки этого этапа: полный набор ноды на Linux / Node 24.21 — 140 успешных без пропусков; backend — 536 успешных и 4 платформенных пропуска. Восемь проверок ядра по восстановлению прошли, включая ожидание живого соединения при смене политики. Это не заменяет сквозную проверку всей установленной системы; `go test -race` этого изменения пока не выполнен из-за отсутствия C-компилятора в Windows PATH.


### Сохранённая доставка временной политики (готовится к выпуску)

Панель сохраняет запрос до обращения к ноде. `POST /api/limits/quota-recovery/nodes/:uuid/held-policy` принимает только `generation` и `requestId`; автор берётся из действующей сессии администратора. Повтор с тем же идентификатором использует исходные экземпляр ядра, журнал, SHA-256 блокировки и ревизию. Другой автор или другая нода не могут переиспользовать этот идентификатор. Успешный повтор возвращает сохранённое подтверждение доставки, а не утверждение о текущей готовности ноды.

`GET /api/limits/quota-recovery/nodes/:uuid/held-policy/:request` возвращает исходный запрос, подтверждение и историю попыток. Параметр `after` продолжает историю по 20 попыток. Оба маршрута требуют действующей браузерной сессии администратора; API-токен, включая `*`, не подходит.

Миграция `20261016190000_recovery_policy_jobs` добавляет неизменяемый контекст операции и журнал попыток. SQL-транзакция не остаётся открытой во время сетевого запроса. Захват операции истекает через 90 секунд: после падения процесса запрос можно повторить, а просроченный обработчик не перезаписывает подтверждение новой попытки. Незавершённый ответ или откат SQL не создают новую выдачу и новую ревизию при повторе.

Сверка состояния базы включает сохранённые запросы и подтверждения; временные блокировки обработчиков не меняют результат сверки. Проверены потерянный ответ, конкурирующие запросы, просроченный обработчик, откат фиксации, смена поколения восстановления, запрет изменения истории и постраничное чтение. Dump/restore отдельной базы сохранил все строки 96 таблиц, состояния 14 последовательностей и контрольные суммы 172 миграций. Общий backend-набор: 536 успешных, 4 платформенных пропуска, ошибок нет; настоящая HTTP-проверка охватывает все 29 маршрутов восстановления.

Полного возобновления трафика здесь ещё нет: подтверждение исходных пакетов трафика и безопасное снятие общей блокировки остаются следующими этапами. Изменения пока не собраны и не опубликованы.


### Подготовка ноды из интерфейса (готовится к выпуску)

В разделе сверки резервов откройте «Проверки нод». Кнопка «Пауза для восстановления» предупреждает о приостановке трафика и требует подтверждения. Отмена ничего не отправляет; подтверждённая пауза блокирует повторное нажатие для того же поколения. Это не перезапуск ноды и не очистка расхода.

Внутри ноды доступна «Подготовка приостановленной ноды»: список сохранённых операций, подтверждение доставки и история попыток. Обе истории листаются по 20 записей. Новый `GET /api/limits/quota-recovery/nodes/:uuid/held-policy?generation=...&after=...` позволяет найти операцию после перезагрузки браузера; идентификатор не требуется вводить вручную. Всего проверено 29 защищённых маршрутов восстановления, включая новый список.

Идентификатор текущей операции сохраняется в браузере до POST. Неизвестный исход допускает только повтор с тем же идентификатором; просмотр старой успешной записи не разрешает заменить незавершённую. При запрете хранилища браузера запрос не отправляется. Сохранённое подтверждение не выдаётся за текущую готовность ноды. Сворачивание блока сохраняет состояние; случайное переключение окна не запускает повторную доставку.

Проверены настоящие React-компоненты с транспортной фикстурой: русский интерфейс 320 px, персидский 390 px с RTL и страницами 20/5, английский 1280 px, китайский 320 px при ошибке загрузки. Проверены потеря ответа, перезагрузка с тем же идентификатором, запрет новой операции при неизвестном исходе, отмена/подтверждение паузы, переход к подготовке, отказ хранилища без POST. Кнопки нового шага на телефоне имеют область нажатия не меньше 44 px. Все четыре перевода синхронизированы; прежние значения не изменены. SQL-проверка списка отдельно подтвердила привязку к ноде/поколению и страницы 20/2.

Полное возобновление трафика, подтверждение исходных пакетов расхода и независимые профили по портам ещё не завершены. Эти проверки интерфейса и SQL не заменяют сквозной прогон установленной панели, ноды и ядра. Сборка и выпуск пока не выполнены.


### Запоздавшие запросы и перезапуск ядра (готовится к выпуску)

После восстановления обычное обновление политики привязано к подтверждённому поколению восстановления, SHA-256 действующего состояния, текущему экземпляру ядра и журналу ноды. Привязка передаётся только во внутреннем HTTP-заголовке `x-remnacust-recovery-proof` (`v1:generation:digest:coreProcessId:instance`). Она не добавляется в JSON Xray, клиентские конфиги, сохранённую политику или общие заголовки Axios. Запоздавший запрос с прежней привязкой, даже с очень большой ревизией, не проходит к подготовке журнала или записи файла.

Пока нода находится в `FENCED`, обычный ACK расхода отклоняется до обращения к ядру; сохранённый пакет не очищается. ACK и постановка на паузу используют один барьер управления нодой. Чтение сохранённого расхода не снимает паузу. После `RELEASED` обычному ACK также нужна текущая привязка. Состояние с повреждённым маркером или остановленным ядром не выдаётся за отсутствие обязательного восстановления.

Экземпляр ядра в привязке относится к работающему процессу. У самого сохранённого пакета после перезапуска может оставаться прежний экземпляр ядра: исходные `coreProcessId`, номер, digest и содержимое пакета не переписываются. Нода отдельно проверяет работающее ядро и идентичность журнала, а нативный протокол проверяет исходный пакет.

Панель хранит ограниченный кэш привязок по соединениям (не более 10 000). Обычный успешный ACK не требует дополнительного чтения полной политики. Если нода отклонила старую привязку, панель обновляет её и допускает один повтор с тем же пакетом; другой номер или digest не создаётся. При действующей паузе повторного ACK не будет. Ноды без истории восстановления сохраняют прежний путь из одного запроса.

Проверки: полный набор ноды на Linux / Node 24.21 — 145 успешных, без пропусков; backend — 540 успешных, 4 платформенных пропуска. Проверены JWT/HTTP-заголовок, старые поколения, другой журнал/ядро, повреждённый маркер, отсутствие записей при отказе, барьер ACK/паузы, исходный пакет прежнего ядра и отсутствие лишнего запроса в обычном ACK. Также прошли Go-проверки нативных пакетов учёта и CLI. Это отдельные проверки компонентов и протокола; установленная система целиком и `go test -race` этого изменения пока не проверены.

Этот этап не добавляет команду снятия общей паузы и не разрешает обычный ACK во время восстановления. Отдельная доставка подтверждений после полной SQL-сверки, обработка неизвестных/утраченных источников и итоговый координатор возобновления ещё не завершены. Новых миграций нет; остаётся схема 172. Сборка и выпуск пока не выполнены.
